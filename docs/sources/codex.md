# Source: Codex

- Task: SRC-CODEX-001
- Observed version/account scope: `@openai/codex` 0.129.0 on Linux;
  authenticated non-API-key login detected, with identity and account details
  suppressed
- Inspected: 2026-09-08

## Evidence boundary

This report combines three bounded evidence sets:

1. The installed npm package metadata and the executable behind `codex`.
2. Version-specific JSON Schemas generated by the installed app server, plus
   schema-only inspection of the configured local Codex stores. No transcript
   text, prompt body, credential, account identifier, local user path, or raw
   provider payload was copied.
3. Current OpenAI documentation for the [app server][app-server],
   [non-interactive execution][non-interactive], [configuration][config],
   [authentication][auth], [pricing and quota semantics][pricing], and
   [Codex chat retention][retention]. Current documentation is ahead of the
   installed release in at least two areas noted below, so it is not treated as
   proof of installed support.

The package was not on this shell's bare `PATH`, but its configured npm binary
was present and executable. Invoking that binary reported `codex-cli 0.129.0`;
package metadata reported `@openai/codex` 0.129.0. The same executable exposes
an experimental `app-server` and version-specific schema generation.

An authenticated login was detected without printing its identity. No live
account usage, rate-limit values, private thread, or paid turn was requested.
Consequently, account-specific field population, quota values, and live active
thread notifications are unknown. The configured desktop/app state was
inspected at schema level only; its separate desktop build number was not read.

Safe, repeatable evidence commands were:

```console
codex --version
codex --help
codex resume --help
codex exec --help
codex app-server --help
codex app-server generate-json-schema --out <temporary-directory>
codex app-server generate-json-schema --experimental \
  --out <temporary-directory>
```

## Session and request identity

- `codex resume --help` accepts a session UUID or thread name and says UUIDs
  take precedence. `codex exec resume` can also continue by ID or `--last`.
- Observed rollout filenames end in a UUID, and sanitized `session_meta` records
  contain `id` and `session_id`. The same UUID-shaped identity is used by local
  thread indexing. Use `(source installation, thread/session UUID)` as the
  session duplicate key; names and titles are mutable display metadata.
- The installed app-server schema models a thread containing turns and items.
  `thread/tokenUsage/updated` is keyed by both `threadId` and `turnId`.
  Individual persisted response items also have item/call identities where
  applicable.
- Sanitized session metadata exposes lineage fields including
  `parent_thread_id` and `forked_from_id`. The local state schema separately
  records parent/child spawn edges. Current app-server documentation says
  `thread/fork` returns a new thread ID and can report `forkedFromId`.
- Rollout JSONL records have a top-level `timestamp`; session metadata and local
  indexes carry creation/update timestamps. The app-server `Thread` contract
  and the local state database also distinguish created and updated time.
- The observed local source classifications include CLI, exec, app-server, IDE,
  and several subagent variants. Preserve source and lineage because one user
  task can create multiple related thread IDs.

The configured local store contained:

- dated `sessions/.../rollout-<timestamp>-<uuid>.jsonl` append-style logs;
- a `session_index.jsonl` index;
- a SQLite thread state catalog; and
- a separate desktop/app local thread catalog.

Observed rollout record envelopes use `timestamp`, `type`, and `payload`.
Sanitized record types included `session_meta`, `turn_context`, `response_item`,
`event_msg`, `token_usage_record`, compaction records, world-state records, and
inter-agent metadata. These are useful private import evidence but are internal
storage formats, not a documented compatibility contract.

### Retention and deletion

- `codex exec --ephemeral` is installed and documented to avoid persisting
  session rollout files for that run.
- OpenAI's configuration reference documents `history.persistence` as
  `save-all` or `none`. `history.max_bytes` caps `history.jsonl` by dropping the
  oldest entries. This setting does not document an automatic TTL for all
  rollout, SQLite, app, log, cache, or shell-snapshot state.
- Installed 0.129.0 schemas expose `thread/archive` and `thread/unarchive`, but
  not the `thread/delete` method now described by current app-server docs.
  Current docs say archive moves rollout logs and `thread/delete` permanently
  deletes a persisted active or archived thread and spawned descendants.
  That newer method must not be assumed available on 0.129.0.
- The current Help Center says retained signed-in Codex chats remain until the
  user deletes them. Deletion removes them from view immediately and schedules
  permanent deletion from OpenAI systems within 30 days, subject to stated
  de-identification and legal/security exceptions. Archive is not deletion.
- No automatic local rollout retention period or complete 0.129.0 local purge
  operation was documented or tested. Benchwarmer therefore needs independent
  private snapshots and must treat source deletion as possible without
  assuming that archived source data is gone.

## Incremental import

The installed app-server provides the strongest supported incremental surface:

- `thread/list` accepts an opaque `cursor`, `limit`, `sortKey` of `created_at`
  or `updated_at`, `sortDirection`, and filters for archived state, working
  directory, model providers, source kinds, and search text.
- Its response contains `data`, `nextCursor`, and `backwardsCursor`.
  `nextCursor` continues after the last item. The schema specifically says the
  backwards cursor anchors timestamp sorting so same-second updates are not
  skipped when reversing direction.
- `thread/read` retrieves one thread by `threadId`; `includeTurns: true` adds
  rollout turns and items. A metadata-only list followed by changed-thread
  reads can therefore separate discovery from private content ingestion.
- `useStateDbOnly` avoids scanning JSONL rollouts to repair metadata. Leaving it
  false permits scan-and-repair behavior. Importers should record which mode
  was used because coverage can differ while local indexing catches up.

A safe first algorithm is to page in ascending `updated_at` order, upsert by the
source installation plus `thread.id`, snapshot private content only after a
successful `thread/read`, and persist the opaque cursor only when the whole page
commits. Periodically overlap or rescan recent pages: neither the installed
schema nor current docs promise cursor lifetime across process restarts,
concurrent mutations, archive/unarchive, deletion, or version upgrades.

Direct file import is possible but less stable. Rollouts are append-style JSONL
and the UUID provides an idempotency key, so an importer could retain file
identity, size, modification time, and byte offset. It must detect replacement,
truncation, late compaction records, archive moves, and SQLite/index lag. The
observed desktop catalog has internal update watermarks and observation
sequences, but those tables are not a public API and should not become an
adapter contract without version-pinned fixtures.

## Usage and economics

### Installed 0.129.0 evidence

- The generated `thread/tokenUsage/updated` schema requires `threadId`,
  `turnId`, and `tokenUsage`. Usage has `last` and cumulative `total` objects,
  plus optional `modelContextWindow`. Each breakdown contains input, cached
  input, output, reasoning output, and total tokens.
- Historical local rollout records also contained sanitized usage shapes for
  request/turn/thread totals. The local shape additionally included a cache
  write input category. Because that category is absent from the installed
  app-server notification, raw source fields must be retained rather than
  projected only into the public notification shape.
- The installed `account/rateLimits/read` schema returns a backward-compatible
  `rateLimits` snapshot and optional `rateLimitsByLimitId`. A snapshot can hold
  a metered limit ID/name, plan type, primary and secondary windows, credits,
  and a reached-limit classification. Windows expose used percent, duration in
  minutes, and reset time as Unix seconds. Credits expose balance text and
  boolean `hasCredits`/`unlimited` flags.
- `account/usage/read` is absent from both the normal and `--experimental`
  schema bundles generated by installed 0.129.0. It is therefore unavailable
  through that installed protocol surface even though current docs describe it.
- No paid turn was started solely to elicit
  `thread/tokenUsage/updated`, and no live account rate-limit response was
  retained. Whether all optional rate-limit fields populate for this account is
  unknown.

### Current documented surface, not installed proof

Current app-server docs describe `account/usage/read` as an authenticated Codex
service endpoint with:

- summary fields for lifetime tokens, peak daily tokens, longest-running turn,
  and current/longest streaks; and
- optional daily buckets containing a start date and token total.

The docs say API-key-only and Bedrock authentication do not support this
endpoint. They do not claim per-thread, per-request, per-model, cached,
reasoning, or batch detail in these account buckets. Bucket timezone, update
latency, historical horizon, and correction behavior are not specified.

Current `account/rateLimits/read` documentation adds a multi-bucket view,
workspace credit details, and optional earned reset-credit details. These are
quota/credit observations, not invoices. Pricing docs say ChatGPT plan usage is
shared across local and cloud work and may also be shared with other agentic
features. They also distinguish API-key usage, which is billed at API rates.

No inspected Codex source provides all of the following in one stable record:
actual charge, currency, tax, subscription payment, API list-price estimate,
batch discount, and provider invoice line. Store tokens, quota percentage,
credit balance, subscription expense, and estimates as separate observations.
Do not infer actual cost from token counts or allocate subscription cost to a
thread. Preserve the reporting timezone as unknown unless a source explicitly
supplies it.

## Classification and prompt visibility

Codex provides operational classifications, not a verified semantic taxonomy:

- installed `thread/list` source kinds distinguish `cli`, `vscode`, `exec`,
  `appServer`, subagent variants, and `unknown`;
- local metadata includes source/originator, thread source, model provider,
  model, history mode, memory mode, and agent role/nickname where present; and
- the local thread database records archived state, user-event presence,
  sandbox and approval modes, Git metadata, provider/model, reasoning effort,
  and source.

No inspected installed or documented thread/usage contract exposed a general
provider classification label comparable to topic, safety, or workload class.
Any Benchwarmer classification should therefore retain human or classifier
provenance rather than masquerade as a Codex-provided field.

Prompt and configuration visibility is partial but useful:

- sanitized rollout `session_meta` includes fields for `base_instructions`,
  version, provider, source, context window, dynamic tools, and lineage;
- installed `thread/start` accepts `baseInstructions`,
  `developerInstructions`, arbitrary config, model/provider, sandbox, approval
  policy, personality, service tier, and ephemeral mode;
- installed `turn/start` accepts per-turn model, reasoning effort/summary,
  service tier, working directory, sandbox, approval, personality, input, and
  output schema; and
- `config/read` exposes resolved effective configuration, field origins, and
  optional configuration layers. Current configuration docs define precedence
  across CLI overrides, trusted project config, profiles, user/system config,
  and built-in defaults. Project `AGENTS.md` content is another explicit layer.

These fields do not prove the exact effective provider request. Hidden service
instructions, server transformations, dynamic tool descriptions, selected
skill content, compaction, and provider-side behavior can remain unavailable.
Benchwarmer should privately snapshot accessible layers with capture method,
order, version, and hash, while marking the effective prompt as partial rather
than empty or exact. Prompt bodies and hashes must remain outside the public
repository.

## Import and execution support

### Read/import

- Preferred installed interface: app-server `thread/list` plus `thread/read`.
  It provides stable thread IDs, cursors, timestamps, source filters, archive
  state, and optional full turns without requiring direct database coupling.
- Installed fallback: private rollout JSONL, session index, and SQLite state.
  These offer more raw fields but have no public schema compatibility promise.
- Current docs describe newer experimental paginated `thread/turns/list` and
  `thread/items/list`; they were not established as installed 0.129.0 support.
- `account/usage/read` cannot be an installed importer on this version.
  `account/rateLimits/read` can be feature-gated, but its live account coverage
  remains unknown until a privacy-preserving runtime probe is approved.

### Automation/execution

Installed 0.129.0 supports real execution rather than import only:

- `codex exec` runs non-interactively with explicit sandbox/approval settings,
  JSONL events, final-output files, output-schema constraints, ephemeral mode,
  and resumable session IDs.
- `codex review` provides non-interactive review.
- App-server supports `thread/start`, `thread/resume`, `thread/fork`,
  `turn/start`, steering, interruption, compaction, and streamed item events.
  It also exposes command execution; app-server documentation warns that some
  command surfaces can run outside the thread sandbox.
- The installed CLI can run as an MCP server, and the app-server can generate
  version-matched client schemas.

Schema-only local app inspection also found scheduled-automation tables with
stable automation IDs, status, recurrence, target/project/thread linkage,
working directories, model, reasoning effort, next/last run timestamps, and
execution-environment metadata. No automation row or run was inspected, the
CLI help does not expose a scheduler command, and no task was executed. Treat
scheduled app automation as app/account-dependent and unknown until tested in a
throwaway workspace with an explicit budget and permission policy.

Any Benchwarmer execution adapter must use disposable fixtures, pin the Codex
version and requested settings, capture observed effective settings, enforce
sandbox/network/credential policy, and reserve attempts durably before starting
paid work. Import capability must not be treated as replay equivalence.

## Reconciliation identifiers

- Thread UUID is the stable Codex harness identity across resume help, rollout
  metadata/filename, app-server thread methods, and local thread indexes.
- Turn IDs and item/call IDs provide finer harness-local identity.
  `thread/tokenUsage/updated` directly relates a usage update to thread and turn.
- Sanitized rollout schema inspection observed a `response_id` field on response
  records; no value was retained. No `request_id` field was observed in the
  sampled rollout schema.
- The installed rate-limit contract and currently documented account-usage
  summary do not include thread, turn, response, or provider billing request
  IDs. Account totals therefore cannot be attributed to individual sessions.
- Neither the installed schema nor current docs inspected here guarantee that
  local `response_id` is the provider's immutable Responses API ID or that it
  appears in provider billing exports. Preserve it with provider/model and
  source provenance, but do not use it as an automatic reconciliation match
  until pass-through semantics are verified with sanitized API-key test data.

Absent a verified provider request ID, reconcile conservatively using exact IDs
where available and treat time/model/token proximity only as a candidate match.
Never add overlapping harness usage, account totals, quota consumption, and
provider charges as though they were disjoint.

## Unknowns and risks

- Live `account/rateLimits/read` population for the authenticated account is
  unknown; no account payload was retained.
- Installed 0.129.0 lacks current documented `account/usage/read`; upgrade
  behavior and the first version adding it were not established.
- Active `thread/tokenUsage/updated` emission frequency, corrections, retry
  accounting, and finality were not tested with a paid turn.
- Daily account bucket timezone, retention horizon, pagination, update delay,
  model breakdown, and relationship to local totals are undocumented here.
- Opaque thread cursor durability under concurrent writes, archive/delete,
  process restart, and upgrade is not guaranteed.
- Local JSONL/SQLite schemas are internal and can migrate. App-created and
  CLI-created records may not have identical coverage.
- Installed archive support is not deletion. Complete local deletion behavior
  for rollout, index, database, logs, caches, snapshots, and descendant threads
  was not tested.
- Current official docs document `thread/delete` and richer account usage than
  installed 0.129.0. Every adapter method and field must be negotiated against
  the running generated schema, not assumed from the current website.
- Prompt capture remains partial; configuration provenance is not proof of the
  exact upstream prompt.
- Scheduled automation availability is app/account dependent and was not
  exercised. Execution can mutate files, run commands, use network access, and
  consume quota; tests require disposable workspaces and explicit budgets.
- Provider reconciliation remains incomplete until a controlled sanitized run
  proves the meaning and provider visibility of `response_id`.
